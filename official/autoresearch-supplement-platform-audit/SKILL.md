# AutoResearch 增量审计 + 平台专项检查

版本：1.0.1，2026-11-02。默认执行 A、B 两部分；用户明确只指定某部分时仅执行该部分，并在报告注明范围。

## 文件与规则边界

**A 部分：原版增量审计，完整保留。**

- 先完整读取并执行 [原版 SKILL.md](references/original/SKILL.md)，按其六类逐项检查。
- 读取 [原版 EVAL_CASES.md](references/original/EVAL_CASES.md) 校准边界。
- 两个文件逐字保留，原六类的报告条件、排除项、只读要求、责任判断、100 字主结论及难度判断均不改。
- 原版提及的完整 v0.3.10 基础质检仍为独立工作；本包没有包含或替代其全部检查。基础质检要求的 NOP、研究轨迹或其他证据不由本包增删或豁免。

**B 部分：平台专项检查，单独新增。**

- 完整读取并执行 [平台专项检查](references/platform-audit.md)。默认覆盖 B-C01–B-C04 源包规则，以及 B-准备、B-执行、B-评分三阶段；逐项留痕。
- 读取 [规则来源与兼容边界](references/rules-and-sources.md)。四项源包规则来自平台复盘文档；镜像选择与 tests 装配分支对齐 V4 及原 v0.3.10，不从历史个案推导新的通用门槛。
- 新增平台案例见 [PLATFORM_EVAL_CASES.md](references/PLATFORM_EVAL_CASES.md)，用于验证本部分的决策边界。

A 的排除项和“无必须修改”只约束 A；B 的平台问题只在 B 报告。B 不将平台规则倒灌为 A 的新增第七类，不改写 A 的结论。A 无必须修改、B 发现源包配置不符时，两种结论应同时保留。

**全程只读。**不执行或导入题包代码，不构建、拉取或运行镜像，不运行 Harbor、Verifier、安装或训练，不自动重试、修复、上传、回填镜像或改表。平台信息只读取用户已提供或已授权且当前可访问的记录；无权限的日志记为未读取，不虚构已完成采集。

## 执行顺序

1. 固定本次题包、版本和证据窗口：题号保留大小写，记录来源记录、包哈希（能取得时）、Trial/重试标识及日志来源。不得用相近题号、旧包或另一 Trial 代替当前材料。
2. 按原版完成 A 六类，原版要求完整覆盖会话时不能因增加 B 而只读摘要。原版允许无运行材料时跳过轨迹审查的边界保持不变。
3. 在独立 B 部分检查源包 B-C01–B-C04；将专家提交源包与平台生成的运行配置、镜像地址分开识别。
4. 对可取得的平台材料，依准备、执行、评分三阶段关联第一条致命错误、后续恢复、最终候选及权威成绩。完整阅读关键失败步骤，不以错误关键词、最后一行或平台 Failed 标签直接定根因。
5. 同一根因在 A、B 同时出现时，用同一个问题编号相互引用；各自结论保留，只汇总一次整改动作。不同根因不得因题号相同合并。
6. 复核下列不变量后输出报告：原版未改、B-C01–B-C04 无漏项、三阶段覆盖有说明、实际分数未改写、责任有依据、静态检查没有被表述为实跑通过。

## 分开输出

报告保存位置按用户指定；未指定时在本次独立报告目录生成一份 `audit_report.md`。不得覆盖专家文件或其他审查报告。默认报告包含下列三部分。

### A：原版增量审计结果

保留原版要求的单题主结论和证据明细。附六类覆盖表，每类标注“已检查”或“未执行”，给出材料范围和原因；没有运行材料时不能把未执行的轨迹检查写成已通过。

原版的“证据不足，不下结论”按其自身触发条件保留，不改成“必须修改”。用户明确只查平台时，本部分写“未执行：本次仅平台专项”。

### B：平台专项检查结果

分别列出以下内容，不用一个 PASS 掩盖未执行的环节：

| 区域 | 必填内容 |
|---|---|
| 源包规则 B-C01–B-C04 | 每项为“符合 / 不符合 / 材料未提供 / 不适用”，附具体文件位置；B-C01、B-C02 对题包必查，不能写不适用 |
| 准备、执行、评分阶段 | 每阶段为“正常 / 异常 / 未进入 / 未执行 / 材料未提供”，写出证据、恢复状态；这些是本报告的观察标签，不冒充平台原生枚举 |
| 原始结果 | 原平台状态、错误类型和 reward 按原值保留；单独说明是否对应当前候选及有效正式评分 |
| 已确认问题 | 问题编号、所属阶段/规则、证据、首因或已确认失败点、影响、负责方、具体动作、复检依据 |
| 覆盖限制 | 未取得的构建、运行、回传材料，以及应由哪一侧提供；不把“没有日志”直接说成“没有运行” |

没有实际运行材料时，写“平台静态配置检查已完成；平台运行检查未执行/材料未提供，不作运行成功结论”。B-C01–B-C04 静态符合只证明这四项，不代表全部格式或依赖兼容性已通过。

### 处理清单

按动作分类列出“专家需返修”“平台需处理”“仅记录”。责任边界未明的已确认问题列入平台协调事项。没有已确认问题的类别写“无”。

- **专家需返修**：当前专家源包违反 B-C01–B-C04，或有证据确认题包代码、构建声明、提交接口或评分逻辑需要修改。给出文件、修改动作和验收依据。
- **平台需处理**：有证据确认平台镜像同步/构建服务、网络代理、授权、运行器、挂载、资源路由或回传需要处理。平台缺少诊断材料时列明需提供的材料，不转换成专家历史补跑义务。
- **仅记录**：已恢复且未污染候选/评分的异常、符合预期的结束行为及其他不产生本轮修改要求的事实。
- **责任边界未明**：保留已确认的问题和两种修复路径，列为平台协调事项，不猜测单方归责；只有确认违反专家源包规则的部分才进入专家返修栏。

不设置全局“待核验/待补充核验”作为验收结论；证据覆盖限制按上述区域如实记录。已确认的缺陷必须给出动作，未知事实不包装成失败，也不包装成通过。平台观察到的异常状态与是否需要专家修改是两个判断。

## 交付前自检

- 原版六类各有覆盖记录，主/子/恢复/重试会话的读取范围符合原版要求。
- 平台四条源包规则逐项有判断；官方包源与 npm 指定 bnpm 的例外关系没有冲突。
- 专家源包禁配 `docker_image`，不等于禁止平台生成运行配置引用已构建镜像；专家不承担内部仓库回填。
- 不以 Dockerfile 数量判定合规：复用 Solver 镜像或专用 Verifier 均按实际分支检查，始终保留独立 sandbox、私有材料边界和候选移交；显式指定 Verifier 镜像时，不因地址相同就假定 tests 自动上传。
- 只读工作目录不自动改为可写；只对题目授权写入位置判断实际可用性。
- warning、缓存未命中、恢复过的临时错误不自动成为根因；非零退出、超时、Failed、零分不互相等同。
- 已评分记录仍核对真实候选、权威指标及最终 reward；不补造零分、不覆盖异常原分。
- 平台故障诊断不借机新增卡型校准、3σ、时限差异或历史 NOP 的强制返修规则。
- 未读取、未运行及责任不明均有明确边界；没有声称本包能自动对接平台接口或保证构建成功。
