# 平台模块决策案例

只用于验证 B 部分，不改变 A 原版案例。以下均为合成场景，不是已实跑 Harbor 的结果。检查结论必须由实际提交材料支持；未给出的事实不能补造。

| 场景 | 应有判断 | 不应出现的判断 |
|---|---|---|
| 唯一源配置位于 `workspace/harbor_task/task.toml`，无有效 `docker_image`；构建文件和对应资产存在 | B-C01、B-C02 静态符合；无日志时运行未执行/材料未提供 | 因缺内部镜像 tag 要求专家返修；声称已构建成功 |
| 当前完整包多一份 `backup/task.toml`，即使专家说明不用它 | B-C01 不符合，列出两路径，整理为唯一交付配置 | 随机挑选其中一份并通过 |
| 专家源配置有效设置本地镜像 `docker_image="task-agent:v1"` | B-C02 不符合；专家去掉预构建引用并交齐 Dockerfile 上下文，平台再构建 | 要求专家先访问内部仓库回填；只删除字段就宣称运行修复 |
| 源包无该字段，平台生成的内部运行配置使用已构建镜像地址 | B-C02 不因平台运行配置而失败；检查来源及实际镜像对应 | 全文匹配字段名，误判专家源包有配置 |
| `docker_image` 只出现在注释或说明中 | 不是有效字段，不据此判 B-C02 不符合 | 用关键字命中代替配置解析 |
| 实际 pip 索引指向清华镜像；别处的资产说明也含该 URL | 生效的包源违反 B-C03；定位安装链与替换范围 | 仅凭说明 URL 判失败；删除所有版本和哈希 |
| APT/pip 官方源，npm registry 实际为 bnpm | B-C03、B-C04 符合；bnpm 是指定例外 | 将 bnpm 按非官方源再次拒绝 |
| `.npmrc` 写 bnpm，但后续 `npm install --registry=https://registry.npmjs.org` 覆盖 | B-C04 不符合，以实际生效设置为准 | 只查到 bnpm 文本就通过 |
| 题包未用 npm，平台注入 Agent 的安装另使用 npm | 源包 B-C04 不适用；平台注入故障单独定位 | 强制专家添加无用 npm 命令 |
| APT 官方源返回 403，后面出现 `not signed` | B-P02，确认真实下载拒绝；区分源声明与平台访问责任 | 建议关闭签名验证，或只把最后一行当首因 |
| 日志只有 pip `from versions: none`，无解析上下文 | 说明已确认失败点，平台提供完整日志定位索引/兼容性；不猜底层根因 | 宣布该版本从未发布并要求随意升级 |
| root:root 755 工作目录按设计只读，输出目录可写，平台启动预检拦截 | B-E01 平台核对并调整不适用预检，保持权限与题目约束 | 要求 chmod 777、递归 chown 或开放私有资产 |
| Agent 达到预算后结束；当前候选已完成正式评分，原始指标与 reward 一致 | 分别记录结束原因和有效成绩；无其他证据不生成作者返修 | 因超时自动认定未评分、强制延长单次求解 |
| 环境初始化 `device_type does not satisfy the task GPU requirements` | GPU 初始化专项，核对请求/路由/设备；不直接断言配额或无卡 | 因原版排除卡型而漏掉真实启动失败；强制重新校准 Reference |
| 缺平台启动必需变量 `LLM_API_KEY`，日志不含其值 | 平台按授权注入契约处理，只记录变量名称与作用域 | 要求专家提交密钥、在报告展示明文 |
| Verifier 实际已生成 reward，沙箱提前回收导致下载失败 | B-S02 平台回传/生命周期问题，保留已有原值 | 判专家没写评分器，补造零分 |
| Verifier 从未生成规定 reward，完整日志证明脚本错误提前退出 | B-S01，按实际控制点修评分实现或路径 | 把脚本退出 0/文件非空当有效评分；补空 reward |
| 权威 reward 为 null，辅助文本为 0 | B-S03，不能把辅助 0 当正式数值通过 | 无条件以 reward.txt 优先，或把 null 改成 0 |
| 文本 reward 是最后一个子结果，JSON 是平台实际读取且聚合正确的正式结果 | 不以数值不同自动报冲突；沿权威链验证 | 一见两个文件不同就返修 |
| 首次镜像拉取失败，重试恢复；同一版本最终候选及评分完整对应 | 历史失败仅记录，注明恢复，不要求无关返修 | 永久保留阻断项或删除原始失败日志 |
| 只有静态源包，没有本次平台日志 | 完成 B-C01–B-C04 与可证明的代码检查；运行未执行/材料未提供 | 无必须修改被扩展为平台运行通过；仅因无日志判专家失败 |
| 源依赖使用非官方内部 pip 源，但无新的批准依据 | 按 B-C03 不符合；内部镜像同步不因此失败 | 把排障建议里的内部 wheelhouse 自动当已批准通用例外 |
| 源包缺构建必需文件，`.dockerignore` 还排除了 Verifier 需要的资产 | 按 B-C02/B-P12 报明确路径和上下文缺陷，按根因去重 | 创建空资产或将私有 Hidden 拷给 Agent 以求通过 |
| A 六类无必须修改，但 B-C01 确认存在两个 task.toml | A 原结论保留，B 独立要求源包返修 | 改写 A 六类结论，或用 A 的排除项让 B 通过 |

使用组合版验收时还须保留原版 EVAL_CASES 的全部边界；本文件不替代它。

## 镜像分支与 Dockerfile 数量的补充案例（v1.0.1）

沿用上方所有案例；下表只验证本次分支修正，不扩展 A 六类或 B-C01–B-C04。

| 场景 | 应有判断 | 不应出现的判断 |
|---|---|---|
| 一份 `environment/Dockerfile`；平台继承 Solver 镜像，在新 Verifier sandbox 上传 tests；依赖预装、入口与候选读取关系静态成立 | 允许复用分支，不因缺 `tests/Dockerfile` 返修；无实跑材料时仅作静态结论 | 强制补第二份 Dockerfile；声称已实跑成功 |
| 两份 Dockerfile；专用 tests context、预置入口和私有材料均有对应关系 | 按专用构建检查，不假定平台还会自动上传 tests | 仅数到两份就通过；缺评分入口时等待默认上传补齐 |
| 平台显式配置 Verifier 镜像，地址与 Solver 相同，但镜像无 `/tests/test.sh`，运行报入口缺失 | 按显式镜像分支定位装配错误，由平台修配置或准备正确镜像；依实际控制点确定动作 | 因地址相同就断言会上传 tests；无条件要求专家补第二份 Dockerfile |
| 已有 `tests/Dockerfile` 实际被选择，但 COPY 的 grader 缺失或被 `.dockerignore` 排除 | 报具体构建资产缺陷；两份文件不抵消缺陷 | 文件数量足够即通过；创建空 grader |
| 复用镜像未安装评分依赖，Agent 临时装包后可运行，新 Verifier 报缺包 | 按实际依赖准备缺陷处理，在所选镜像补齐依赖 | 依赖 Agent 容器状态；将复用分支本身判违规 |
| 两份 Dockerfile，但已有记录确认 Solver 与 Verifier 共用同一 sandbox | 保留独立环境失败事实，按平台实际控制点处理 | 两份文件证明隔离；掩盖明确反证 |
| 单份或两份 Dockerfile 将最终私有 tests／Hidden 复制进 Agent 可见镜像 | 报私有材料边界缺陷，不以增加／减少文件数量代替修复 | 为解决评分入口缺失而向 Agent 公开私有材料 |
| 合法复用分支只有静态源包，无平台 tag／运行日志 | 完成可做的静态检查，记录运行覆盖限制 | 因未有平台记录自动退回；把静态符合当端到端通过 |
| 两侧共用的同一镜像烘焙了私有 tests，平台又显式指定该镜像作 Verifier | 同时检查实际选中分支和 Agent 可见性，指出私有材料暴露 | 只关注 Verifier 能评分，忽略 Agent 也能读取私有材料 |
