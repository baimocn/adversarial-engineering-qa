# 平台专项检查：配置、准备、执行与评分

本文件是组合 Skill 的 **B 部分**，补充原始六类审计未枚举的平台交付与运行问题。原始六类审计继续按原文件执行，不以本文件取代，也不把本文件中的平台失败自动归为出题人问题。

## 依据与适用范围

- 来源：[Harbor 1074题执行复盘：失败原因、解决办法与验收清单（2026-10-26）](https://bytedance.larkoffice.com/docx/IZ3OdIbl2olhOwxPvq3cqF0xnQS)，本次读取的文档 revision 为 **1145**。
- 文档的 1,074 题及各失败数量是历史批次统计，不是新题验收配额，不要求当前题复现同类错误，也不把该批次成功率当作当前题通过标准。
- 静态配置规则依据来源文档末节“需加入质检skill的rule”。准备、执行与评分检查依据前三个阶段的原因族、解决办法及证据边界。
- B 部分只读题包和已经授权提供的平台导出、日志与运行产物。不构建或拉取镜像，不执行题包、Docker、Verifier、训练或下载脚本，不修改原包、权限或分数，不启动新 Trial。
- 没有平台日志时，仍完成可完成的静态配置与源码检查；运行阶段按实际材料注明覆盖范围，不把未执行写成运行通过，也不把缺日志猜成运行失败。

## 一、先建立本题、源包和 Trial 的对应关系

1. 记录题目 ID、来源记录 ID（已有时）、本次完整包标识／已有 SHA256、配置版本，以及平台 Trial／任务 ID。题号大小写有意义；不同作者或不同来源记录的同号题不得合并。
2. 分开当前正式 Trial、已替换 Trial、诊断 Trial 和历史 Trial，不累计成多道题。历史日志仅证明对应历史版本和运行，不自动证明当前返修包。
3. 优先读取已经提供的原始准备错误、ByteBuild 构建步骤与完整 stdout/stderr、`batch.log`、原生 `result`／`complete.json`、Agent／Verifier 日志、原始指标、reward、产物归档回执和 HDFS／其他产物位置。这是材料查找清单，不是假定平台一定使用这些固定字段或路径。
4. 以实际数据读取关系关联：源包 → 构建配置／实际镜像 → 环境初始化 → Agent → 最终候选 → Verifier 实际输入 → 原始指标 → 平台采用的 reward → 归档／回传。
5. 已有授权导出里带日志链接时，可以读取对应材料。仅有链接但当前无法访问时，记录具体缺少的日志和最小导出请求；不得声称已经集成自动拉取，也不得请求或展示密钥明文。
6. 判断最先造成终止或错分的错误。普通 warning、缓存未命中、非终止的重试与后续连带错误，不单独当首因。已恢复且未污染候选或分数的历史错误不要求返修。

## 二、当前专家交付包的四项静态规则

下表用于**专家提交的源包**。平台为了执行而生成的内部运行配置、已成功构建的镜像 tag 或 digest，应作为平台运行证据单独记录，不要求外部专家访问内部镜像仓库。

| 编号 | 检查内容 | 有直接证据时的处理 |
|---|---|---|
| B-C01 | 项目中只保留一份名为 `task.toml` 的任务配置，位置为 `workspace/harbor_task/task.toml`。先定位完整提交包根目录，避免把外层压缩包目录误当任务根目录。 | 多份任务配置、任务根目录不唯一、缺少该文件或位置不符合当前交付要求，指出每个实际路径并要求专家整理。不得随机挑选配置继续当作通过。 |
| B-C02 | 专家源包的 `task.toml` 不配置 `docker_image`；按 `workspace/harbor_task/environment/Dockerfile` 及其实际构建上下文准备镜像。来源文档的 `Dockfile` 按 Docker 标准文件名 **`Dockerfile`** 理解。检查文件非空、基础镜像引用、实际 `COPY`／`ADD` 路径和 `.dockerignore` 是否一致。 | 源配置仍有有效的 `docker_image` 项，或 Dockerfile／构建必需资产缺失，按实际文件要求专家修正。只有注释或说明文字出现字段名不算配置。删除字段不等于构建已成功；也不能因为尚无内部 tag 而否定完整的专家 Dockerfile 交付。 |
| B-C03 | 依赖下载使用发行版／软件包生态的官方源，不配置清华等非官方镜像源；核对实际生效的源设置，包括 Dockerfile、被引用的安装脚本和源／包管理配置。npm 按下一项指定例外处理。 | 能定位实际使用的非官方依赖源时，列出文件、行和替换范围；保留必要的版本、哈希、签名与资产校验。不得以“换官方源”名义删除版本约束或安全校验；基础镜像仓库、模型资产地址不能仅凭不是包管理官方域名就套用本项退回。 |
| B-C04 | 使用 npm 包时，构建流程将 npm registry 设置为 `https://bnpm.byted.org`，例如 `npm config set registry https://bnpm.byted.org`，并核对后续实际 npm 安装命令使用的配置。未使用 npm 的题目标为不适用。 | 实际 npm 安装仍使用不符要求的 registry 时要求修正；不机械要求出现某一条相同文本，等价且真正生效的配置也可。该项是来源文档明确指定的源，不能同时按 B-C03 当作非官方源拒绝。平台侧访问或代理认证失败再按准备阶段定位。 |

补充边界：

- 专家提供 Dockerfile、构建上下文和依赖／资产材料；平台负责在实际构建身份与网络环境中构建、发布和选用内部镜像。完整源码交付不等于已完成平台构建，两者分别报告。
- Dockerfile 数量不作为独立验收门槛。复用 Solver 镜像时可省略 `tests/Dockerfile`；采用专用构建时核对该文件及其实际上下文。两种方案始终要求 Solver／Verifier 为不同 sandbox，不能因只用一份 Dockerfile 就取消独立 Verifier。具体按下述实际镜像分支核对。
- B-C03 采用来源末节的官方源规则；前三节的内部包源／离线 wheelhouse 建议不自动构成源包例外。另有批准的替代方案时保留批准依据，否则不自行放行。平台内部镜像仓库不等于包管理依赖源。
- 预构建镜像配置会使平台跳过相应 Dockerfile 的重建时，应核对**本次实际构建与选用路径**。删除专家源包字段之后，平台可以在生成的运行配置中写入成功构建的内部镜像；不要把平台生成配置误认成专家违规配置。
- 本文件没有新增“必须提交镜像 tar”“必须专家回填内部 tag”“必须补跑 NOP”或“必须重新求解”要求。已有 NOP 或历史运行材料可以读，不能用未被要求的新材料制造返修项。

### 独立 Verifier：按实际选中的镜像分支检查

本节对齐 V4 revision 70 与原 v0.3.10 的镜像选择／tests 交付口径，只消歧 B-C02 的检查方式，不新增第五条源包规则，也不代替完整基础质检。

| 实际选中分支 | tests 的装配方式 | 本模块核对重点 |
|---|---|---|
| 继承 Solver 镜像／构建：未显式选择专用 Verifier 镜像，且未选择 `tests/Dockerfile` | 在**新的独立 Verifier sandbox** 上传私有 tests；可省略 `tests/Dockerfile` | 可上传的评分入口、私有材料的读取／生成／安全注入路径、镜像预装的评分依赖，以及最终 artifacts 的移交与读取。不得仅因没有第二份 Dockerfile 要求返修。 |
| 实际采用 `tests/Dockerfile` 的专用构建 | 通常以 `tests/` 为 context，预置 `/tests/test.sh` 和评分实现；Hidden 按已声明的预置／生成／安全注入路径提供，不走默认 tests 上传分支 | 实际 context、COPY／ADD、`.dockerignore`、入口、依赖与提交物读取关系。两份文件存在不等于构建或评分已成功。 |
| 平台运行配置显式指定 `verifier.environment.docker_image` | 按专用镜像分支核对入口及评分实现的预置、Hidden 的声明装配方式；不是默认 tests 上传分支 | 即使镜像地址或 digest 与 Solver 相同，也不能据此假定会自动上传 tests。核对镜像内容／已有运行材料；另有适配装配方式时须有目标版本依据。平台生成配置造成装配错误时，按控制点处理，不自动要求专家补第二份 Dockerfile。 |

本次对齐的镜像选择顺序为：显式 `verifier.environment.docker_image` → `tests/Dockerfile` → Solver 的镜像／构建。必须先识别**平台实际采用的配置和目标版本**，再判断 tests 上传或预置；仅看文件数量、相同镜像地址或源包中的意图说明均不足。其他目标版本有明确适配依据时按其实际规则记录，不猜测默认行为。此处没有放宽原题包适用的 Compose 或其他部署限制。

所有分支均保留以下边界：

- `environment_mode = "separate"`，Solver／Verifier 使用两个独立 sandbox；Agent 结束后由平台移交最终 artifacts。声明 separate 不等于本轮已验证运行时隔离，已有相同 sandbox 身份等明确反证不能忽略。
- 公开 Dev 保留给 Agent；最终私有 tests／Hidden／Reference 不进入 Agent 可见环境。不能为解决 Verifier 缺入口而把私有 tests 烘焙进同时给 Agent 使用的镜像。
- Verifier 所需依赖在实际采用的镜像中准备，不依赖 Agent 临时安装的包、缓存或未移交文件。复用的是初始镜像，不是 Agent 结束时的容器状态。
- 缺少平台装配或运行材料时按既有证据边界记录覆盖限制，不仅因缺日志或未有内部 tag 判专家失败，也不宣称已成功运行。

## 三、准备阶段：25 个原因族

逐项检查现有材料是否命中以下原因族。表中的“定位与修复边界”是基于已确认错误的处理方向，不是要求每题都提交 25 份证明。没有命中时，不假设失败；有失败时，不只读最终退出码。

| 编号 | 原因族／典型信号 | 定位与修复边界 |
|---|---|---|
| B-P01 | Docker Hub 网络不可达；`registry-1.docker.io` 连接失败、`Errno 101` | 核对准备与实际构建身份的网络／代理、基础镜像来源和拉取阶段。平台可同步可访问内部镜像并锁定 digest；专家源包仍按 B-C02 交付 Dockerfile。网络故障不能仅归为题目代码错误。 |
| B-P02 | APT 索引或安装包下载 403；随后出现 `not signed` | 找第一条下载拒绝、发行版与有效软件源；后续签名错误可能只是连带结果。使用符合 B-C03 的源并由平台修复必要访问条件，不用 `trusted=yes`、关闭签名或不安全仓库绕过。 |
| B-P03 | Python 分发、索引或环境兼容性；`from versions: none`、无匹配分发、PyArrow／NumPy 不兼容、缺 z3 等 | 同时核对 Python 版本、架构、CUDA、实际索引及完整 pip 日志。不能只凭 `none` 宣称版本从未发布，也不能静态一律归因于版本号。区分源包依赖不相容和平台未提供约定环境。 |
| B-P04 | 基础镜像引用或拉取授权；`pull access denied`、`insufficient_scope`、短镜像名误解析 | 核对完整仓库、tag／digest、架构与实际工作负载身份。引用错误由控制引用的一方修；访问权限由平台按授权补齐。404 不自动等于权限问题。 |
| B-P05 | Git 仓库访问、锁与推送；`index.lock`、push 超时、pull 失败、分支冲突 | 读取实际 Git 步骤、HTTP／授权错误和远端结果；使用任务隔离的干净 clone、分支和有界幂等重试。不得删除活跃任务锁或把平台发布故障归为专家未重跑。 |
| B-P06 | 发布包结构或归档损坏；无／多任务根目录、非有效 ZIP、RAR 截断 | 核对实际格式、唯一任务根目录与 B-C01；传输损坏先重取正确原包，源包确有缺陷再返修。不得借用相似题号资产或随机选择任务根。源包变化保留新版本依据。 |
| B-P07 | 已解析到具体 wheel 后下载拒绝或代理错误；403、代理 DNS 530 | 读取失败 wheel 的下载域名、代理、出口与授权。区分下载失败和分发不存在；平台解决访问／缓存，必要离线资产保留哈希和完整性校验，不关闭 TLS。 |
| B-P08 | 镜像层上传会话失效；`blob upload unknown`、上传 PUT 404 | 定位 builder→registry 上传步骤、会话、代理与并发。平台重建上传会话、有界重试，并回读 manifest／digest；不要求专家改变评分实现。 |
| B-P09 | 模型或公开资产下载链路；429、TLS 链失败、308、资产超时 | 记录实际资产和状态；平台可授权缓存、退避、修正证书和重定向。仅说“超时”不能猜模型缺失；不能绕过受保护资产授权或校验。 |
| B-P10 | npm 包管理代理认证失败；407 | 找 npm 元数据／tarball 请求与构建身份代理配置；核对 B-C04。不能称为 Codex 进程启动失败；平台修复代理或指定源访问，凭据不得写入包或长期镜像层。 |
| B-P11 | 镜像 manifest、digest 或代理异常；无法解析、代理 not found、ECR blob 401、成员 manifest 未发布 | 同时核对源 registry、代理、架构、媒体类型和认证。代理 not found 不证明上游镜像不存在；平台负责同步／发布时应验证不可变镜像实际可读。 |
| B-P12 | 构建上下文资产路径缺失；BuildKit `COPY`／cache key 路径 not found | 对照源包、context、COPY、`.dockerignore` 和资产清单。缺少必需文件或排除规则冲突可静态确认；不能创建空目录糊弄构建，不能向 Agent 暴露 Hidden。 |
| B-P13 | APT 安装退出 100，但没有首条致命错误 | 请求已有失败步骤完整 stdout/stderr 与 Dockerfile 行；区分 403、缺版本、临时目录、协议等。当前只确认安装步骤失败，不凭退出码指定替换方案。 |
| B-P14 | APT 固定版本在当前源缺失 | 核对发行版、updates／security 源、源快照和已有 `apt-cache policy` 证据。采用可复现且可用的版本集合，不一律取消锁定；静态版本字符串不是已证实安装失败。 |
| B-P15 | Python 依赖约束冲突；`ResolutionImpossible` | 读取完整解析报告，定位冲突依赖对及 requirements／constraints；由控制依赖集合的一方修成相容集合，不盲目升级全部依赖或删除约束。 |
| B-P16 | 题包准备脚本或资产校验失败，首因不明；`prepare_image.py`、`uv sync` 等退出 | 补已有 traceback 和失败子命令 stderr，区分解析、资产下载和校验。不得删除准备脚本的资产校验换取成功。 |
| B-P17 | APT 证书包配置所需临时目录缺失 | 核对 Dockerfile 步骤顺序、目录、属主及实际构建环境；修复目录初始化后验证证书链，不关闭证书验证。 |
| B-P18 | 评分资产／锚点不一致；fixture 哈希不一致、初始化 Hidden 目录缺失 | 由授权 Verifier 维护者核对 manifest、映射、已有锚点与隔离复制。检查的是已发生的资产装配／评分阻塞，不扩展为重做 GPU／3σ 校准；不得删除校验或暴露 Hidden。 |
| B-P19 | 准备进程访问源包路径 `Permission denied` | 核对实际身份、父目录与文件 mode、解包／挂载方式。区分原包必需可执行权限与平台读取身份问题；不递归 chown／chmod 原始资产。 |
| B-P20 | bootstrap 解释器无法启动；例如 `/opt/runtime/bin/python` | 核对解释器文件、动态链接、PATH、启动脚本权限和平台启动契约；依据实际控制点修复，不随意换运行时或提升 root。 |
| B-P21 | sudoers 语法校验失败；`visudo` | 源配置规则有误时按最小授权修正并核对已有校验依据；不开放无约束 sudo。平台注入规则有误由平台修复。 |
| B-P22 | Docker Hub manifest 请求明确 429 | 与网络不可达分开；平台使用授权缓存／同步、降请求和按响应退避，不提高并发掩盖限流。 |
| B-P23 | 创建用户 UID 1000 冲突 | 对照基础镜像既有用户、约定 UID 与 Dockerfile 创建步骤，保留题目权限契约；避免随意换 UID 破坏只读资产或输出目录权限。 |
| B-P24 | sudo 资产所有下载源失败，但 HTTP 首因未留存 | 记录已有证据能确认的失败范围；请求各源状态、代理与 DNS 日志后定位授权／网络／资源失效。不能猜根因或删除 sudo 资产约束。 |
| B-P25 | Python 依赖哈希校验失败 | 核对锁文件、预期 wheel、缓存与镜像来源；可信来源确认后才能修正哈希。不删除 `--require-hashes` 或无条件接受下载物。 |

## 四、执行阶段：9 个原因族及两个专项定位

| 编号 | 原因族／典型信号 | 定位与修复边界 |
|---|---|---|
| B-E01 | 工作目录可写性预检拦截 | 先读只读设计、Agent UID/GID、mode、挂载、允许输出位置。题目按设计只读时，由平台修正不适用预检，保留真实权限；题目需要写入的输出位置才按契约修复。不能把拦截一律解释为专家应开放整目录。 |
| B-E02 | HOME／临时目录／日志／PID 权限失败 | 核对实际挂载后的身份与路径，保证本次运行的 HOME、缓存、临时文件、日志和规定输出位置可写；只读题目资产仍保持只读。依据谁控制目录与身份分责。 |
| B-E03 | Agent 超时 | 保留终止与 reward 原值，区分预期预算截止、Solver 自行耗尽预算、平台启动／资源故障及有效候选是否完成评分。正常到达 Agent 时限且有可信评分，不因此要求作者改题或延长单次求解。没有评分时查真实终止链；不把全部超时都视为平台故障或正常成功。 |
| B-E04 | 其他非零 Agent 退出；`NonZeroAgentExitCodeError` | 读取第一条非零命令、stderr 与启动契约；非零退出是现象，不默认归为权限或作者错误。确认环境／依赖／路径故障才给相应修复，不提升 root 掩盖问题。 |
| B-E05 | Agent 安全拒绝；`LLMRefusalError` | 保留模型拒绝与任务授权证据，交负责人核对平台适用政策／支持渠道。不能把拒绝当作无评分的代码故障，也不要求改写提示绕过安全限制。 |
| B-E06 | 执行终态存在，但没有已发布原生摘要 | 区分确已结束与仍在运行，核对 batch 日志、退出码、`complete.json`、原生 result 及上传回执。缺摘要不等于仍在跑，不能补造分数；首因不足时明确缺哪份既有平台材料。 |
| B-E07 | 环境健康检查失败；例如 `test -S /run/public-eval.sock` | 查服务启动日志、socket 创建、可见挂载、顺序与就绪条件。网络／socket 配置本身不作为新增作者规则，但实际依赖服务未就绪导致运行失败必须记录；不能简单删 healthcheck。 |
| B-E08 | 环境创建／cgroup 资源设置失败；`CgroupCreationFailed`、quota invalid argument | 记录请求 ID、实际资源参数及后端错误，平台核对支持范围和路由。不得自行缩减题目资源来“通过”；已有一次成功不能证明此前明确故障不存在，但已恢复且不影响当前结果不再要求返修。 |
| B-E09 | 其他沙箱生命周期异常；任务／会话不存在 | 对照创建、清理、重试与回收日志，避免复用已删除会话；由平台确认生命周期首因。不仅凭错误表象要求专家重打包。 |

**GPU 初始化专项：** 出现 `device_type does not satisfy the task GPU requirements` 时，查 `gpus`、`gpu_types`、`device_type`、CPU/GPU 环境管理器路由及实际设备证据。该信号证明初始化契约不相容，不能直接写成“没分配 GPU”或“配额不足”。本文件不增加卡型验收／换卡校准要求；但已经发生的环境创建失败不能因原始审计排除“卡型配置本身”而被漏报。

**环境变量专项：** 缺 `LLM_API_KEY` 等平台启动必需变量时，核对授权注入／环境文件契约和变量存在范围。只记录名称、是否存在及注入环节，不读取或输出值，不把密钥写入题包、表格或命令日志。平台注入失败由平台修复；题包错误地要求不该由专家交付的凭据，应同时说明契约冲突。

### 只读工作目录的验收边界

确认“需要修复权限”之前，同时核对：指定身份能否启动、设计只读路径是否仍拒绝写入、规定输出目录是否可写、HOME／日志／临时目录是否可用、Verifier 与提交契约是否保持不变。

运行器确实支持、负责人确认后才能调整不适用的工作目录预检，例如 `workdir_access=off`。不在静态报告中宣称该设置已经生效，不递归 `chown` 整题，不使用 `chmod 777`。

## 五、评分阶段：3 个原因族

| 编号 | 原因族／典型信号 | 定位与修复边界 |
|---|---|---|
| B-S01 | 缺评分文件；`RewardFileNotFoundError` | 核对 Verifier 退出码、stdout/stderr、实际生成位置与平台读取位置；区分没生成、路径不符和生成后回传失败。静态明确错误由控制评分／读取路径的一方修；不能补造 `0` 让协议通过。 |
| B-S02 | Verifier 目录下载失败；`DownloadVerifierDirError` | 若沙箱产物存在，检查挂载、下载／传输、归档和会话回收；平台修复回传。脚本退出 0 不能证明产物已归档，已归档产物也须与本次候选对应。 |
| B-S03 | 非数值评分；`null`、`NaN`、`Infinity` | 读取实际被平台采用的文件、评分异常分支与序列化；正常评分必须是协议接受的有限数值，失败分支应明确记录失败。不能把这些值改成有效零分，也不能仅检查辅助文件而忽视真正读取的 reward。 |

所有评分问题都核对最终候选→Verifier 输入→原始指标→平台 reward→归档。负分或零分可能是有效成绩，也可能是默认占位，不能仅凭数值判断。多 reward 文件不自动构成冲突；先确认权威读取关系及聚合规则。

Agent 已有完整有效候选时，可以提出由平台评估是否支持仅修复评分／回传后独立复评分；本 Skill 不自行执行。平台不支持或候选不完整时，由实际负责人确定重跑与版本记录，不默认要求专家重新跑长时研究或补历史 NOP。

## 六、责任、证据和检查结果的写法

### 定位责任

- **出题人**：当前源包结构、源码中真实生效的错误配置、必需构建资产缺失、相互矛盾的提交／评分路径、依赖集合自身不相容或评分实现错误。
- **平台／rollout**：实际构建身份的网络和代理、镜像同步发布与拉取授权、Git／registry 发布链路、挂载与身份、平台注入、环境初始化、资源路由、沙箱回收和产物回传。
- **双方待分责的已确认问题**：先写已确认故障和最小修复位置，缺哪份平台契约，再给两种可行修复方向；不能因责任未定否认故障，也不能把所有平台准备失败都打回专家。
- 同一错误可能同时涉及专家源配置和平台访问条件，分别指出实际需要的动作；不能只根据日志出现的文件名猜负责人。

### 按证据覆盖表述，不创造全局“待核验”结论

| 证据状态 | 应写内容 |
|---|---|
| 已证实 | 写出实际文件／日志位置、Trial／版本、首因和影响。需要修改时明确负责人、动作和复查材料；不只写“请补充核验”。 |
| 材料未提供 | 写明哪个环节没有可读材料和最小获取方式。例如“未提供本次 ByteBuild 失败步骤 stderr；请平台导出该步骤日志，当前不能区分源下载403与包版本缺失”。这不是自动确认失败或运行通过。 |
| 未执行 | 本次仅静态检查，未执行构建／平台运行；报告可证明的配置问题和已读历史事实，不宣称当前运行成功。 |

缺少某份材料本身，仅在当前已明确的交付义务要求该材料、或存在已确认问题而需要该材料完成修复验收时，才成为对应责任方的具体动作。不要因平台尚未运行而要求专家补造当前实跑、镜像 tag、完整历史 sessions 或 NOP。

### 同时区分三个判断

1. **运行链路情况**：准备、Agent 执行、Verifier 评分、回传分别完成到了哪里；正常时限截止／Solver 放弃等记录为实际终态，保留原因。
2. **成绩可信性**：是否真实对应本次候选、完成规定评分且已被平台正确读取。有效分数不等于达到题目目标；存在有限数值也不自动证明有效。
3. **作者是否需要返修**：只取决于作者控制的当前缺陷及本次明确规则。平台故障、历史正常超时或未提供平台日志，不自动生成作者返修项。

因此可以同时成立：“Agent 在预算截止时结束；最终候选取得可信评分；无作者返修项”。也可以成立：“平台存在非零 reward，但只有失败占位／旧候选结果；当前运行链路未完成；由平台修复”。不人为覆盖原分数，也不把任一局部检查的通过扩展成完整验收通过。

## 七、与原始六类审计的关系

- 原始第一类覆盖实际平台／镜像／环境故障、候选与成绩错配；原始第五类覆盖承诺资源确实不可用。B 部分补充配置规则、平台材料定位和 25／9／3 个原因族，不替代这些判断。
- 原始审计排除时间配置差异、网络配置本身、卡型校准和候选内部错误分类等，不表示应忽视已经证实的镜像拉取失败、环境初始化失败、服务无法启动或评分产物回传失败。B 部分将其作为**平台交付／实际运行事实**记录，按真实控制点处理，不借此扩展作者校准或长时求解要求。
- 原始审计的泄漏、技术边界失效、题面冲突、优化内容不参与评分等仍须全部检查。平台专项通过不能替代六类审计；六类“无必须修改”也不能证明本文件四项静态规则或平台运行均通过。
- 同根因、同修复动作合并报告。已经在原始六类报告的问题，B 部分可关联原因族补充平台证据，不重复制造多条返修。
