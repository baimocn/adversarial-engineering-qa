# AutoResearch 补充审计（v0.3.10 增量）

本 Skill 是对 v0.3.10 `autoresearch-task-qa` 的增量补充，增加了：

- **轨迹审查**（一、二）：运行是否完成、solver 是否实际违规
- **静态检查**（三、四、五、六）：检查题面与实际执行是否一致，以及 solver 可见材料是否泄漏私有信息或参考解

v0.3.10 基础 Skill 负责检查方法空间、Baseline 合理性、提升真实性和一般实现问题；本 Skill 不重复这些检查。文中六类检查可以独立执行，不需要读者理解基础 Skill 使用的检查编号。

## 背景概念

**solver / Agent**：负责阅读题目、研究方法并生成最终候选的解题程序。本文件统一称为 solver；轨迹里的主 Agent、子 Agent 都属于 solver。

**Verifier**：在独立评分阶段读取最终候选、运行正式数据并计算成绩的程序。

**reward**：平台最终采用的成绩值。

**rollout**：负责把实际镜像和运行环境交付给 solver 与 Verifier 的一方。

**题面**：solver 运行时能看到的全部文字说明和目标描述，常见形式是 `instruction.md` 或任务配置中的描述字段。题面告诉 solver 要优化什么、能用什么、不能做什么、怎么提交、怎么评分。审计时先通读题面全文，以题面实际内容为准，不预设文件名。

**solver 可见材料**：题面以及 solver 在实际环境中能读到的文件、数据和公开接口。目录名称不决定可见性；应以实际打包、挂载、权限或运行记录为准。仅供 Verifier 使用且 solver 实际不可见的私有文件不属于 solver 可见材料。

**参考解**：出题人自己的完整解法，包括公式、算法、参数、结构和实现步骤。参考解应当只存在于 solver 实际不可见的私有区域；不能仅凭目录名称判断其是否私有。

**Baseline / Starter**：出题人放在 solver 可见区的对照实现和起点代码，供 solver 参照和验证。读取它们属于正常研究行为，不等于看到了参考解。

**Hidden 与 Dev**：题目可能有两套评测数据。Dev 是公开开发集（如果题目提供），solver 可以反复使用来验证和改进方法。Hidden 是正式评测集，只在 Verifier 内使用，solver 不能直接看到它的标签或答案。正式成绩由 Hidden 决定，Dev 只是开发辅助。不是所有题目都有 Dev。

**权威成绩来源**：平台最终读取并用来生成成绩的记录。必须沿着实际读取关系判断，不能仅凭文件名或后缀指定优先级。调试文件、兼容性文本或单次子结果没有被平台最终读取时，不是权威成绩来源。

**合规提交**：严格遵守题面所有规则的 solver 最终产物。第三、四、五类只报告会影响正常合规提交的问题。第二类只有在技术边界失效且出题人或 rollout 能在不破坏正常研究用途的情况下修复时，才报告已经发生的违规。第六类只有在泄漏内容能直接帮助针对正式目标解题，或本次已经实际使用时，才报告为必须修改。畸形提交、主动攻击以及未实际利用的理论漏洞不报告。

## 目标

核对题面、solver 可见环境、历史轨迹、最终候选、Verifier 和 reward 是否真实对应。默认结论是"无必须修改"；不得为了显得审计充分而补充假设性问题。

## 只读要求

- 只读取题目包、配置、轨迹、最终产物、Verifier 源码和运行记录。
- 不执行或导入题包代码，不运行 Docker、Verifier、安装脚本或训练，不反序列化模型，不拉取镜像。
- 必须复跑才能确认时，先请求授权；没有证据时不猜测结果。
- 不得假定 solver 能取得题包外内容。只有题包已经包含该内容，或轨迹、工具返回、实际环境记录证明 solver 已经成功取得时，才算可获得。URL、WebSearch/WebFetch 工具、模型服务地址或“允许联网”的文字都不能单独证明内容可获得。

## 可报告问题的六类

六类分为两组：

- **轨迹检查**（一、二）：需要阅读运行记录
- **静态检查**（三、四、五、六）：只读题包和配置即可完成

只检查下面六类问题，并逐项完成检查。发现一类问题后，仍需检查其他类别。
符合对应报告条件且证据充分的问题，写入“必须修改”；不符合条件或属于排除范围的，不写入修改清单。证据不足时，按文末“证据不足，不下结论”处理。

---

### 轨迹检查

### 一、运行未完成或成绩没有对应真实候选

**判断**：Agent、Verifier 有没有实际启动并跑完？最终候选有没有被评分？最终候选 → Verifier 实际输入 → 原始指标 → 最终 reward 是否对应同一次运行？候选标识可能是哈希、路径、版本或其他实际记录，不能预设固定字段名。

**报告**：
- Agent 或 Verifier 因平台/镜像/环境故障未启动或异常退出且未恢复
- Verifier 读取了旧候选、错误的模型检查点（checkpoint）、其他任务产物或残留结果
- 最终 reward 与 Verifier 原始指标不一致
- 报告声称完成评测但实际只运行了空候选

**不报告**：
- solver 自行放弃或主动终止
- 非权威的调试文件与权威成绩不同，但权威指标到 reward 链路正确
- 出现过错误但随后恢复并完成有效评分，且错误没有污染候选或成绩

---

### 二、轨迹实际违规

**判断**：轨迹是否证明 solver 成功越过或利用失效的技术边界，读取私有内容、修改受保护对象、操纵评分或使用被隔离的外部执行能力？只有请求、没有成功结果，不算违规；理论漏洞不算。

只要最终候选经过题面规定的完整公开协议或正式 Verifier 评测，候选与成绩对应且分数合法有效，solver 研究过程中的工作目录或临时目录差异不报告。读取私有内容、修改受保护对象或操纵评分仍按本类检查。

只有本应通过题包接口、文件读写限制、环境隔离或评分器检查落实的技术边界失效时，才把已经发生的违规写入必须修改。

如果题面只是用文字要求 solver 不做某种行为，但无法在不破坏正常研究用途的情况下通过技术手段准确禁止，那么 solver 违反这类要求属于 solver 自身行为，不向出题人或 rollout 提出修改。

**报告**（还必须满足上面的技术边界和可修复条件）：
- solver 成功越过或利用失效的访问限制，读取原本应隔离的私有内容
- solver 成功修改固定数据、Verifier、reward 或其他受保护对象
- solver 绕过或利用失效的执行隔离，把正式计算转移到题面禁止的外部服务或额外机器

**不报告**：
- 只有请求，没有成功结果
- 只有理论上的攻击方式，本次没有使用
- 题面仅用文字要求 solver 不做某种行为，但没有能够在保留正常研究用途的同时准确落实该禁令的技术边界；solver 违反这类行为要求不向出题人或 rollout 报告

负责方按实际修复位置判断：修改题包公开内容或接口归出题人；修改实际挂载、读写范围或隔离方式归 rollout。

---

### 静态检查

### 三、题面说明与实际执行不一致

**判断**：solver 可见材料明确写出的指标、公式、输入、输出、资源或评分规则，与实际执行路径是否冲突？冲突是否改变正常合规提交的运行或分数？

**报告**：
- 题面明确写出的规则、指标或资源描述，与实际评分路径直接矛盾
- 正常合规提交因此运行失败或被错误评分

**不报告**：
- 题面没写某个边界，审计员自行假设"任意大文件/字段/进程/计算规模都应被接受"
- 代码写法不够严密、缺少额外防护、存在理论反例，但当前合规提交不会失败
- 时间限制及其差异，不据此提出修改要求
- 公开 Dev 与正式环境有差异（除非题面明确承诺二者相同）
- 题面中的 Baseline/Reference 校准流程，包括 seed 数、重复次数、配对方式、3σ、计时校准和轻微 Baseline 数值偏差，即使未被 Verifier 执行，也不按“题面说明与实际执行不一致”报告

---

### 四、要求优化的内容不参与评分

**判断**：题面明确要求 solver 优化或产出的内容，在实际评分路径中是否被读取？

**报告**：从候选输出追到最终指标，证明该内容完全没有进入评分。

**不报告**：
- 研究日志、解释、运行过程数据、时间字段和来源证明附件（即使题面要求提交，除非用户另行要求研究过程真实性审计）
- 内容已用于评分，只是审计员认为“权重不够”

---

### 五、承诺的资源不可用

**判断**：题面明确承诺可用的数据、工具、目录、依赖或公开 Dev 入口，在题面规定的正常用法下是否确定不可用？

**报告**：
- 题面明确承诺、solver 按承诺方式正常调用、实际返回失败、失败未修复并影响研究或评分
- 没有运行记录时，源码能够直接证明题面规定的正常调用必然失败

**不报告**：
- solver 没有实际使用某项资源，且源码也不能证明正常调用必然失败
- 只有运行环境的文字提醒或 solver 自报“无法使用”，没有真实调用失败或必然失败的源码证据
- 一次临时错误，随后已恢复
- 公开 Dev 与正式环境有差异但未承诺相同

---

### 六、私有信息或参考解泄漏

**判断**：solver 可见材料是否包含 Hidden 样本、标签、答案、私有评分信息，或参考解的具体公式、算法、参数、结构和实现步骤？公开材料是否足以重建上述私有内容？这些内容是否能够直接帮助 solver 针对正式目标选方法、调参数、构造候选或影响成绩？

**必须修改**：
- solver 可见材料包含具体 Hidden 样本、标签、答案、私有评分信息或参考解实现细节，并且这些内容能直接帮助针对正式目标选方法、调参数、构造候选或影响成绩
- solver 可见材料足以重建上述内容，并且重建结果能直接用于针对正式目标选方法、调参数、构造候选或影响成绩
- 轨迹证明 solver 已经获得并使用上述内容

**不报告**：
- 重建需要包外数据，但 solver 在实际环境中没有取得该数据的能力，本次也没有获得或使用
- 公开 baseline 或 starter 中的对照实现
- 参考解分数、随机种子（seed）、通用研究方向
- 只能知道公开数据来源、切分比例或大致分布，但不能重建具体 Hidden 内容
- 只能提出理论利用方式，没有具体内容可见或可重建

---

## 明确不进入报告的内容

以下内容不作为需要修改的问题报告：

- 时间限制、超时配置、各阶段时限之间的关系，以及实际耗时差异

- 网络策略、联网能力、禁网声明、白名单、模型端点、Socket/HTTP 接口或网络配置本身；但轨迹证明 solver 已经成功使用题面明令禁止的外部服务或额外机器时，按第二类实际违规报告
- GPU 卡型、允许型号、实际型号或卡型校准
- 候选错误被归为哪一种内部错误
- 缺字段、错类型、嵌套列表等畸形输出是否被严格拒绝
- 只影响主动攻击或违规提交的反作弊加固
- 准备文件、源码或数据的哈希值是否陈旧，以及上游地址变化、内容固定或数据归档问题
- 参考解分数、旧数据 revision、归一化区间或 3σ 校准强度
- 随机种子（seed）的披露或可见性
- Dev 数据、Dev 标签、Dev 真值的可重建性或可见性（Dev 是开发辅助，不影响正式 Hidden 评分）
- 注意：公开材料可重建 Hidden 时，仍需满足第六类“必须修改”的直接用途或实际使用证据；否则不报告
- 代码写法、额外防护、理论反例或未被实际调用的维护性问题

---

## 报告问题时需要什么证据

所有问题都必须写明证据位置，并按问题类型说明事实和影响：

### 运行、题面一致性、评分和资源问题（一、三、四、五）

必须同时说明：

1. **题面或配置依据**：题面、配置或公开材料实际承诺了什么；
2. **实际执行方式**：候选、公开入口、Verifier 或平台实际上如何执行；
3. **具体触发方式**：哪个正常合规的提交或正常操作会触发问题；
4. **实际影响**：已经发生或必然发生的运行失败、成绩对应了错误候选、错误评分或错误 reward。

### 已发生且需要出题人或 rollout 修复的违规（二）

必须同时说明：

1. 哪份题面、题包接口契约、访问限制、挂载或隔离设计规定了该技术边界；
2. solver 实际做了什么；
3. 操作是否成功，以及环境、文件或工具实际发生了什么变化或返回了什么；
4. 对私有内容读取，说明实际返回了哪些私有内容；对其他违规，说明该行为如何影响研究、候选、运行状态、正式指标或成绩；
5. 哪个技术边界失效，以及出题人或 rollout 能采取什么不破坏正常研究用途的明确修复。

另行写明：`规则遵守：不合规`，以及 `成绩可信性：可信 / 不可信`。只有满足本类技术边界和可修复条件的问题才进入报告；此时成绩链正确不影响该违规结论成立。

### 私有信息或参考解泄漏（六）

至少说明：

1. 泄漏或可重建的具体内容；
2. 该内容为什么属于 Hidden、私有评分信息或参考解；
3. solver 如何实际获得，或公开材料如何足以重建；
4. 重建是否依赖题包外的数据或服务；如果依赖，solver 在本次实际环境中通过什么已验证的方式取得它，必须给出成功返回或等价直接证据；只有 URL、题面称允许联网、WebSearch/WebFetch 工具存在或 solver 理论上可以下载，不足以证明可取得；
5. 该内容能否直接帮助 solver 针对正式目标选方法、调参数、构造候选或影响成绩；
6. 本次轨迹是否实际重建、获取或使用。

按第六类标准决定“必须修改”或“不报告”。不要求泄漏同时造成错误 score；但判“必须修改”时必须证明内容本身具有直接解题或针对正式目标的用途，或本次已经实际使用。只有请求没有返回、只有文件存在但无法证明 solver 可见、只有随机种子或参考解分数时，不报告。

没有题面或配置依据时，不能仅以“题面没写”为理由新增合同；第二类已经发生的违规和第六类私有信息泄漏按各自证据要求判断。

## 合并规则

同一根因且修改动作相同，只报告一项。不得按调用链的不同阶段拆分，也不得把前置校验缺失和后续异常各算一次。同一私有内容同时涉及第二类和第六类时：内容已经直接放在 solver 可见材料中，按第六类报告；solver 通过越过或利用失效的访问限制才取得内容，按第二类报告。

## 执行步骤

### 第一步：定位输入材料

**静态检查（三、四、五、六）**至少需要题面说明、任务配置、solver 可见材料和 Verifier/评分代码。没有轨迹、最终产物或运行结果时，仍应完成静态检查。

**轨迹检查（一、二）和难度判断**还需要实际运行材料，例如：

1. solver 运行时的消息记录、工具调用、工具返回和文件读写；子 Agent 轨迹也可能存在；
2. solver 最终提交的候选；
3. Verifier 实际读取的候选标识、原始指标和最终 reward。

具体文件名、字段名和目录结构以实际材料为准。缺少运行材料时，跳过第一、二类和难度判断，不得因此跳过第三至六类。

### 第二步：建立对应关系

1. 有运行材料时，必须从第一条到最后一条完整覆盖主 Agent 会话、全部子 Agent 会话以及恢复或重试会话；不能只读主会话后半段或最终总结。记录每条会话的消息总数、实际读取范围和未覆盖部分。
2. 从完整轨迹中找到 solver 最后选择或写入的提交，记录候选标识；标识可能是哈希、路径、版本或其他实际记录。
3. 确认 Verifier 实际读取了哪个候选，并与 solver 最终选择的候选对照。
4. 从 Verifier 原始指标追踪到平台实际使用的最终 reward，确认聚合和方向正确。
5. 读题面提取所有明确承诺：优化目标、评分指标、可用资源、禁止行为、提交格式。

### 第三步：逐类检查

对每个检查项：

- 先读对应文件的具体位置，不凭记忆或推断。
- 发现疑似问题后，先查看“明确不进入报告的内容”。属于排除范围的，不写入修改清单。
- 按问题类型补齐“报告问题时需要什么证据”一节要求的证据；证据不足的，不列为必须修改。

### 第四步：合并、反证检查与复核

- 原因相同且修改动作相同的问题，合并为一条。
- 如果运行记录中存在非空成绩，报告第一、三、四、五类问题前，应先核验该成绩是否确实对应当前候选、是否完成正式评分，并把核验结果作为反证。
  - 如果候选、Verifier 输入、正式指标和最终 reward 完整对应，就不能再报告“本次没有完成”或“当前候选没有评分”。
  - 非空数值也可能只是表示失败的占位分数（例如 -1）、旧候选成绩或错误产物，不能仅凭存在分数就认定运行有效。
  - 问题涉及本次没有走到的其他正常合规场景时，当前成功不能自动否定问题；但必须给出题面明确允许的具体场景、实际执行路径，以及该场景必然失败或错分的证据。
- 第二类实际违规按该类证据要求判断，并说明规则遵守和成绩可信性。第六类泄漏按该类证据要求判断；只有同一事实同时构成第二类违规时，才需要说明规则遵守。
- 对“运行未完成”“私有信息或参考解泄漏”“实际违规”“要求产出不参与评分”四类，独立重读关键文件复核一次。

### 第五步：判定负责方

先定位最先导致问题的环节和最小修改动作，再判断负责方。问题已经确认，不代表负责方已经确认；不要仅凭“路径错误”“不能写入”或“运行失败”等表面现象直接归责。

- 修改题面说明、提交接口、公开代码、公开数据、公开入口或 Verifier 评分逻辑 → 出题人
- 修改实际交付镜像、运行环境中的目录挂载和读写设置、solver 与 Verifier 的隔离方式，或平台资源分配 → rollout
- 提交路径问题还需确认平台约定：出题人偏离平台约定时归出题人；题包使用平台约定、实际环境却没有提供时归 rollout
- 没有材料说明平台约定，或出题人改路径与 rollout 改环境都能解决时，问题仍然可以成立；负责方写为 `[出题人或rollout]`，并分别给出两方可采用的解决思路

## 输出

### 判定负责方

每个需要修改的问题必须写明负责方。允许三种标记：

- `[出题人]`：证据已经确认修改题目说明、题包代码或 Verifier 即可解决
- `[rollout]`：证据已经确认修改实际交付镜像或运行环境即可解决
- `[出题人或rollout]`：问题已经确认，但现有材料不能确定应修改题目一侧还是运行环境一侧；必须同时写出两种可行解决思路

**出题人** — 管题目向 solver 作出的说明、提交接口和评分逻辑。具体包括：
- 题面写什么、不写什么
- solver 可见的公开代码、公开数据和公开入口
- 提交接口的路径、文件名、输入输出和格式要求
- 公开 Dev 的实现和可用性
- Verifier 的评分公式、指标和边界条件
- 题面禁令是否在题包和公开入口中技术落实

**rollout** — 管实际交付给 solver 和 Verifier 的运行环境。具体包括：
- 实际交付镜像中的依赖、系统库、工具和资产
- 工作目录、提交目录和私有目录在实际运行环境中的挂载和读写设置
- solver 与 Verifier 的实际隔离方式
- 平台实际分配的资源
- 平台实际注入的文件、变量和限制

**判断方法**：先找控制该修改动作的一方。修改题目声明或题包代码 → 出题人；修改实际交付镜像或运行环境 → rollout。提交路径问题必须额外核对平台约定；没有平台约定或其他责任边界证据时，写 `[出题人或rollout]`，不得猜单一负责方。

**例子**：

| 问题 | 负责方 | 原因 |
|---|---|---|
| 题面说 Hidden 不可见，但题包公开代码能重建 Hidden 数据 | 出题人 | 修改题包公开代码或题面声明 |
| 题面、任务配置和 Verifier 对提交目录的要求互相冲突 | 出题人 | 统一提交接口说明和题包中的消费路径 |
| 已有平台规范明确要求提供某提交目录，题包按规范使用，但实际运行环境没有提供 | rollout | 修正实际运行环境，使其符合平台规范 |
| 已确认 solver 无法按题面路径提交，但没有平台路径规范，无法确定是题面路径写错还是实际环境未提供 | 出题人或rollout | 出题人可把提交路径改成实际可用路径；rollout 可提供题面声明的可写提交目录 |
| Verifier 按 B 归一化，但题面承诺按 A 评分 | 出题人 | 修改 Verifier 或题面指标说明，使二者一致 |
| 实际交付镜像缺少题面承诺可用的 numpy，solver 合法 import 失败 | rollout | 更新实际交付镜像 |
| 题面禁止使用某项私有输入，但题包公开接口仍直接返回该输入 | 出题人 | 修改题包公开接口或删除不真实的禁令 |

### 必须修改

每题使用以下三种单项模板之一：

`题目ID：[出题人] 修改条目；原因。`

`题目ID：[rollout] 修改条目；原因。`

`题目ID：[出题人或rollout] 问题和原因。出题人可……；rollout 可……。`

第三种只用于问题已经确认、但现有材料无法确定责任边界的情况。必须同时写出两种可行解决思路。

两方各自都有确定需要修改的问题时，用句号分隔：

`题目ID：[出题人] 修改条目；原因。[rollout] 修改条目；原因。`

第三、四、五类只写已经确认会影响正常合规提交运行或评分的问题；第一类写已经发生的运行或成绩链问题；第二类只有满足该类技术边界和可修复条件时，才写已经发生的违规；第六类只有满足该类“必须修改”条件时才写入必须修改。

每题先写一行主结论，含题目 ID 不超过 100 个 Unicode 字符。随后另附证据明细，证据明细不计入 100 字限制。证据明细按“报告问题时需要什么证据”一节的对应格式填写。

没有问题时写：

`题目ID：无必须修改。`

### 证据不足，不下结论

只用于用户明确要求检查、且属于六类范围，但现有材料缺少必要证据的事项。写明缺少的具体文件或记录以及最小获取方式。不得放入模型自行设想的问题。

### 题目难度（不做验收要求）

难度与质量问题分开。仅在成绩可信后，根据首次有效改善时间、最终成绩、方法复杂度和剩余改进空间判断：

- `明确偏易`
- `有偏易迹象`
- `暂不判偏易`
