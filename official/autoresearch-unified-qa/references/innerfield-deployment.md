# 当前内场工作环境边界

本节保留与当前Harbor/资源/隔离要求兼容的已明确平台边界，不提供另一套历史验收版本。依据为原平台交付与执行规范及已确认的内场工作环境组织要求；最新算法规范没有重述平台每个实现细节，不等于允许绕过已分配资源或私有评测边界。unknown只表示具体底座未指定，不猜网络/storage/内核支持，也不单独阻断静态。

## 容器组织与GPU使用要求

1. 每个sandbox使用单容器。Agent在平台已分配的沙盒内开发、训练、推理和调试，需要GPU时直接使用该沙盒已分配设备，不能把另一个计算沙盒/容器作为任务工作环境。
2. 题面、启动脚本、broker或运行时不得要求/依赖额外申请、创建、启动或使用计算sandbox/工作容器。Docker-in-Docker、通过宿主Docker socket启动sibling Docker、任务调用Docker SDK另建GPU worker均不支持。已有的远端 GPU 沙盒也不能承担本任务训练/推理/调试，不能以“连接已有”代替新建规避。
3. Solver和最终Verifier由平台/框架分别管理，仍为独立sandbox，可复用初始镜像并按artifacts交接；框架正常创建这两个环境不属于任务自行部署额外工作环境，也不要求Verifier在Agent开始前创建。
4. 专家/平台在解题前准备当前镜像、构建依赖是正常准备。当前sandbox内的普通子进程、本地训练/推理及使用已分配多卡的多进程均不因“多进程”违规；不能仅凭Dockerfile或任务外docker build示例判运行时另起环境。
5. 正常模型服务请求、允许的模型/公开资产准备与平台通信，不等于把计算交给额外工作环境；仍按当前数据预置、网络工具与私有边界审查，运行时临时下载不能补足必需基础依赖。通过SSH/HTTP/SDK让其他计算sandbox/容器执行训练、推理或调试则按用途判断，不能仅看协议名/地址。

## 证据与责任

沿实际选用配置、启动脚本、运行封装、Dev/最终评分入口读取谁发起、处于准备还是解题阶段、程序最终在哪里执行。没有Compose文件不证明没有额外部署；仅有Compose/Docker/broker关键词也不证明依赖额外工作环境。本版没有新增自动识别任意部署代码的能力。

题面或有效调用链已明确要求/依赖不支持的额外工作环境时，是当前交付缺陷，按H03及具体当前harbor_format/resource_limit/private_boundary事实记录；即使平台拒绝该部署要求也不能使题包合规。若包本身合规，仅Agent自行申请/使用额外环境，记录真实行为与被拒绝的请求，不能仅凭这类 Agent 行为推定作者题包存在部署缺陷，也不自动宣布已有正式分数无效；按真实成功结果和影响分责。

无法确认额外执行位置仅写具体平台/调用覆盖范围，不把unknown当已违规，不向专家索要新内网探针。已有当前正常运行失败仍据控制点修复；静态成立不能冒称本次实际GPU/容器隔离已验证。
