# 上下文分片与跨文件接口

## 1. 不让长上下文兼任证据数据库

先运行 `collect_evidence.py`，把文件身份、源码符号、语法调用线索和声明位置落盘。模型只加载当前问题所需分片，已确认结论写成带路径和行号的短笔记。

不要把“我之前看过”当证据。每个结论都能从清单、分片、原始文件或运行日志重新定位。

## 2. 完整分批

- 以文件清单为分母，不以模型记住的文件为分母。
- 分片默认保留目录局部性；跨分片 producer/consumer 必须另建关联笔记。
- 每片记录：已读文件、确认声明、候选接口、未解决关联、需动态验证项。
- 最后核对所有分片均有处置；未读分片不得从终稿消失。
- `.git`、依赖缓存可排除，但排除项要计数并说明；交付源码不能因目录大而不审。

## 3. 单一契约权威

配置字段、命令、输出 schema 和报告结构各只设一个权威来源。其他文档引用它，不另写一份容易漂移的“简化契约”。

本 Skill 的报告结构只以 `report-schema.json` 为准；校验器从该 schema 读取结构规则。

## 4. 跨文件四联单

每个能力至少追这四类对象：

1. **Producer**：谁生成配置、模型、清单、结果或返回值；
2. **Consumer**：谁读取、解包、评分或执行；
3. **Config**：默认值、环境变量、命令行和覆盖优先级；
4. **Docs**：公开声明、示例命令、边界和限制。

任一环缺失都要显式记录。README 与代码一致还不够，还要确认实际调用链使用了该配置和本次产物。

## 5. AST 索引的边界

`collect_evidence.py` 的符号和调用是语法级候选：

- 不执行导入；
- 不做类型推断；
- 不保证解析动态分发、反射、monkey patch、装饰器副作用或框架注册；
- 不把同名函数自动当成同一语义对象；
- 不声称是精确调用图。

它适合发现入口和关联线索，不适合单独证明“所有调用均已覆盖”。

## 6. 返回契约扫描的边界

`check_return_contracts.py` 对可静态确定的 tuple/list 返回和解包做检查：

- 能发现同一函数不同分支返回数量与调用方预期不一致；
- 能给出返回点和调用点行号；
- 对动态返回、星号展开、无法唯一解析的调用记为未解析或覆盖限制；
- 不用“未报错”推出“所有动态契约正确”。

发现候选后打开源码核对；需要证明实际失败路径时，在授权沙箱运行最小反例。

## 7. 接口审查顺序

按以下顺序减少遗忘：

1. 公开声明和配置中的入口；
2. 入口对应的实际文件与 cwd；
3. 函数/脚本的全部退出和返回分支；
4. 调用方接收、异常和退出码处理；
5. 下游输出文件和最终评分/结果；
6. 与文档、测试和历史证据的差异。

不要只沿单一调用链顺读；从声明、producer、consumer 和攻击面分别反向追踪，再合并。

## 8. 多路独立性

独立红队从当前声明和产物开始，不读取旧报告结论。后续可比较路线结果，但比较前不得共享判级。多路使用同一提示词、同一旧报告和同一包内自证，不等于独立验证。
