# 本次需要调整的要求

| 要求 | 常见旧写法／问题 | 本轮怎么改 |
|-|-|-|
| 任务配置只留一份 | 完整源包混有当前、backup 或 history 中多份 task.toml。 | 单题源包只保留 workspace/harbor_task/task.toml；历史配置另归档或改成说明材料。批次多题分别整理，不混在一个单题包中。 |
| 专家交 Dockerfile，平台准备内部镜像 | 直接把示例 docker_image、本地镜像名或不能访问的内部地址交上来。 | 专家源 task.toml 删除有效 docker_image 项，交齐 environment/Dockerfile、构建上下文、依赖与资产。内部镜像由平台构建／选用并写入平台运行配置，专家无需访问内部仓库或回填 tag。 |
| 依赖使用规定的下载源 | pip／APT 等实际使用清华等非官方源，或只改说明、未改安装流程。 | 非 npm 包管理依赖使用发行版／对应生态官方源；检查 Dockerfile、安装脚本和包管理配置实际生效的设置。保留依赖版本、哈希与签名校验。 |
| npm 单独按指定源配置 | npm 仍走其他 registry，或后续安装命令覆盖了已设置的源。 | 使用 npm 包时，实际 registry 使用 https://bnpm.byted.org；未使用 npm 的题目无需新增 npm 步骤。构建代理或认证失败交平台处理，不把凭据写进题包。 |
| GPU 目标与候选列表分开 | 只有其他卡可选，或把历史其他卡结果直接标成 H20／L20 实测。 | 内场 GPU 题实际用 H20，L20 也接受；CPU 题不增加 GPU。候选列表可含其他型号，但须支持并实际选用 H20／L20。仅因列表还有其他候选，不要求删除；已有结果保留真实设备标签。 |
| 两侧独立运行，不强制两份 Dockerfile | 以为一份文件必不合格，或两份文件就证明隔离；评分依赖留在 Agent 临时环境。 | 允许复用初始 Solver 镜像，或使用专用 Verifier 镜像／构建；始终使用两个独立 sandbox。复用时可省略 tests/Dockerfile，评分依赖预装，私有 tests 交给新 Verifier。 |
| 作者校准不变成 Solver 完成义务 | 题面要求“达到作者校准的 3σ 才完成，否则继续运行”“必须进入 Reference 校准区间”“单次 Agent 跑满作者研究的 10 小时”。 | 从 Solver 题面、选优和完成条件迁出这些作者校准义务。作者自己的 B/R 成对评估、适用统计校准及研究证据保留；题目算法本身合理使用的 3σ 不按关键词删除。 |

仍需遵守本题实际评分协议、提交接口和真实可用资源。上表关于题面的调整，迁出的是作者验题／校准义务，不取消候选正常评分所需的质量门和程序运行限制。

# 容易误解或与原文档有变化的地方

## 题面中的三标准差（3σ）：这次改的是要求对象

原标注文档中有“题面写明有效提升阈值（如 3σ）”的表述，因此此前按原文把三标准差写进题面的题目，本轮也需要按下面的边界调整。**作者仍需完成题目校准；不要把作者校准门槛直接写成 Solver 必须达到的完成、选优或延长运行义务。**

| 容易混淆的内容 | 本轮如何处理 | 应保留在哪里 |
|-|-|-|
| 作者验证 Baseline／Reference 的提升是否超过随机波动，适用时采用 3σ 等统计校准 | 保留作者验题要求及真实成对评估记录，不因调整题面就取消提升充分性检查。 | 专家说明、正式评分／校准协议和 optimization_evidence 中的 B/R 证据。 |
| Solver“必须达到作者校准的 3σ 提升才算完成，未达就继续运行” | 从 Solver 题面、完成条件和选优说明中移除这种作者校准义务；任务真实目标、评分指标和合法候选要求仍保留。 | 作者校准留在专家材料；Solver 只承担实际任务合同。 |
| 把 Reference 校准区间或作者的长时研究要求一并交给 Solver | 迁出“必须达到 Reference 校准区间”“单次 Solver 必须跑满作者研究时长”等条款；作者研究证据与平台／候选真实预算分别保留。 | 作者研究及校准说明；真实运行预算仍按本题约定。 |
| 题目算法本身使用 3σ，例如异常值检测或真实任务的统计规则 | 按实际用途保留，并使题面与实现一致；不能搜索到“3σ”就全部删除。 | 对应算法、真实评分协议及其必要题面说明。 |

**专家自查：**检查 instruction.md、Solver 可见的 README／提示词、完成条件及选优说明，避免同一作者校准义务在其他位置残留；作者的 Baseline／Reference 校准和已有真实记录继续保留。



# 返修包按这个方式准备

## 检查文件、构建上下文和提交目录

```text
提交包/
├── workspace/
│   ├── harbor_task/
│   │   ├── instruction.md
│   │   ├── task.toml                 # 本题源包唯一一份
│   │   ├── environment/
│   │   │   ├── Dockerfile
│   │   │   └── 公开Dev、Starter和对应构建资产
│   │   └── tests/
│   │       ├── test.sh               # 正式评分入口（按任务约定）
│   │       ├── 评分代码和私有材料／生成与注入说明
│   │       └── Dockerfile            # 专用构建时提供；复用可省略
│   └── reference/                   # 专家参考解，Agent不可见
├── expert_evidence/                 # 专家说明及适用的研究／自检记录
└── optimization_evidence/           # 适用的正式Baseline／Reference证据
```

environment/ 和 tests/ 通常分别作为各自构建上下文。COPY／ADD 的来源必须真实存在于实际 context 中，且没有被 .dockerignore 排除。公开 Dev 和 Starter 可交给 Agent；最终私有测试、Hidden 标签和 Reference 实现不得复制到 Agent 可见环境。

运行时 /workspace/solution 是本教程使用的候选提交路径；它与源包中的参考解目录不是同一个用途。若本题采用其他获准路径，初始化、题面、artifacts 声明、平台移交和评分读取位置必须一致。

```toml
artifacts = ["/workspace/solution"]

[verifier]
environment_mode = "separate"
```

## 按所选镜像方案检查评分材料

| 方案 | 专家需要准备 | 改完核对什么 |
|-|-|-|
| 复用 Solver 初始镜像 | 提供可交给 Verifier 的 tests／评分入口和私有材料说明；在复用镜像中预装评分依赖。可以只有一份 environment/Dockerfile。 | 平台用同一初始镜像创建全新 Verifier sandbox，上传 tests 并接收候选。不要依赖 Agent 临时装包、缓存或未移交文件。 |
| 专用 Verifier 构建 | 提供 tests/Dockerfile 和实际 context 内的评分入口、实现及依赖；Hidden 写清预置、生成或安全注入方式。 | 核对入口、COPY、忽略规则和候选读取路径。两份 Dockerfile 存在本身不能证明构建和评分成功。 |
| 平台显式选择 Verifier 镜像 | 说明所需入口、依赖和私有材料装配方式，供平台选用正确镜像。 | 即使 Verifier 镜像地址与 Solver 相同，也不能假定 tests 自动上传。平台需核对实际选择分支；不要为补入口把私有 tests 烘焙到同时给 Agent 使用的镜像。 |

# 题面、公开评测与评分逻辑：这些情况需要修正

| 要修的问题 | 怎么识别 | 怎么修改和核对 |
|-|-|-|
| 题面和实际接口不一致 | 题面说只交 method.py，评分器却读取另一文件，或拒绝题面允许的日志。 | 统一题面、解析／白名单、评分入口和提交说明；用一份题面允许的合法提交，沿路径核对到实际被读取的文件。 |
| 公开 Dev／承诺工具不能正常用 | 公开命令指向不存在路径，依赖没安装，工作区白名单拦住 public_eval。 | 修正入口、复制、依赖或访问范围；用题面原用法检查 Starter／合法候选能得到指标或明确失败信息。源包正确但平台缺挂载／依赖时交平台处理。 |
| 要求优化的产物没有参与评分 | 要求提交模型，评分器却只查文件非空；要求输出动态图，实际只用固定图。 | 让评分器实际加载、执行或解析要求提交的产物并用于指标计算；或同步调整题目说明。不能以“文件存在”代替实际评分。 |
| 最终候选与成绩对不上 | 选出最佳模型后，移交了最后一次失败实验；评分读取旧 checkpoint／旧 reward。 | 恢复并完整保存最终选中的候选，统一 artifacts 和读取路径；核对“最终候选→Verifier 输入→原始指标→平台 reward”属于同一次运行。 |
| 具体私有内容能被 Agent 获得或重建 | 公开代码包含可直接用于解题的 Reference 公式，或公开资产能重建具体 Hidden 标签。 | 把实际私有实现／资产移至可信评分侧，检查镜像、复制、挂载和公开接口。公开 Starter、通用公式、seed 或参考分数不单凭名称判泄漏。 |
| 已有记录证明保护边界被成功绕过 | 候选成功改写可信评分器／reward，或读到本应隔离的标签。 | 针对已发生的失效点修接口、权限或候选执行边界，并确认正常研究仍可进行。平台挂载／身份导致的问题交平台修；被拒绝的请求不等于成功越界。 |

参考解、Hidden 的私有边界与真实评分必须保留。不要为了跑通而删掉评分、把私有标签交给 Agent、只验证模型文件非空，或写一个默认 0 分代替失败原因。

# 平台实际运行中已经发现的八类返修问题

| 实际问题 | 专家怎么改 | 改完看什么 |
|-|-|-|
| Landlock 不可用，训练／评分尚未开始就退出 | 移除可信训练／评分入口对不可用 Landlock 的强依赖，按平台支持的环境执行原训练与评估；保留数据权限、输入和候选边界检查。 | 不支持 Landlock 时仍能走完原流程并出分。不要简单忽略保护失败后开放私有数据，也不要求专家另造一套 Sandbox。 |
| HOME、临时目录或日志目录不可写 | 按实际运行 UID 初始化 HOME、缓存、日志及规定输出目录，保证候选工作目录可写；镜像内共享临时目录 /tmp、/var/tmp 使用兼容的 1777 权限。只读题目资产保持只读。 | 在干净环境、相同运行身份下，初始化和公开入口可用；不依赖手工修权限，不把整题 chmod 777。 |
| 服务或资产只靠镜像 ENTRYPOINT 初始化 | 在平台实际调用的正式入口显式接入必要准备、完整性和服务就绪检查；重复启动应有明确行为。 | 平台直接执行约定命令、不隐式触发 ENTRYPOINT 时，服务和资产仍就绪；固定服务权限和私有边界保留。 |
| 共享 UID 与过低进程上限导致 worker 启动失败 | 核对用户共享计数与本题进程预算，采用目标平台可支持的身份和启动方案；保留候选的资源限制及降权。 | 单题及批量并发时 worker 均能正常启动；不能全局提限、取消降权或把 EAGAIN 一律当 GPU 不足。 |
| 模型／分词器／训练和验证资产未交 | 交齐原版本资产，或明确授权的安全交付／挂载方案、版本、位置、校验和准备方式。仅有 MANIFEST 或“运行时挂载”一句话不够。 | 干净环境能读到真实输入、完成原任务并产生所需产物。不要用空文件、小模型或合成数据替代原资产。 |
| Agent 有候选，Verifier 却收到空目录 | 按当前执行器要求修正 artifacts 声明、来源目录和移交范围，统一接收端与评分读取路径。 | 核对移交前后文件清单及已有校验标识（如 SHA256），确认对应同一候选、Verifier 能实际加载。不要看到空接收目录就认定 Agent 没写代码。 |
| 公开评测产生缓存／日志，污染严格提交目录 | 将可信评估的缓存、日志和工作目录放到评估输出位置；控制可信导入产生的 pyc／\_\_pycache\_\_，保留提交白名单。 | 按“公开评测→立即移交→独立评分”检查，超时收尾也不污染提交目录；不靠临时手删或关闭白名单掩盖问题。 |
| 原子替换文件与单链接检查发生竞态 | 让发布／读取约定兼容已证实的原子替换瞬态；采用有界重开，并保留每次普通文件、无符号链接、链接数、大小和完整读取校验。 | 并发发布／读取稳定出分，符号链接、硬链接、FIFO 和超限文件仍拒绝；不删除安全检查、不无限重试。 |

这些是已确认运行缺陷的处理方式，不表示所有题都存在相同故障。运行链路是否完成与科研成绩好坏分开看：可信评分完成且结果正确对应候选时，低分、负分或质量目标未达到本身不等于运行失败。

# 按平台报错查修改位置

先看最早导致失败的错误，再看后续是否恢复。下列三表覆盖 25 类准备、9 类执行和 3 类评分错误；

## 构建与准备阶段

| 编号／报错现象 | 专家检查和修改 | 平台处理或提供 |
|-|-|-|
| P01 Docker Hub 连不上；Errno 101 | 核对基础镜像完整名称和版本，保留完整构建材料。 | 平台检查构建网络／代理并同步可用镜像；专家无需访问内部仓库。 |
| P02 APT 下载 403；随后 not signed | 检查发行版、官方源及安装配置；保留签名校验。 | 平台导出第一条下载错误，修复代理／访问；不根据后续签名提示盲改。 |
| P03 pip 找不到分发／缺包；NumPy、PyArrow 不兼容 | 核对 Python、架构、CUDA 与 requirements／constraints，补齐实际依赖。 | 平台提供完整 pip 日志及实际环境，区分依赖冲突与索引／环境问题。 |
| P04 pull access denied／insufficient_scope／短镜像名误解析 | 修正自己控制的完整镜像引用、tag／digest 和架构。 | 平台核对拉取身份及授权；404 不直接等同权限问题。 |
| P05 Git index.lock／推送拉取超时／分支冲突 | 题包引用的仓库或版本确实错误时修正该引用。 | 平台检查发布用 clone、分支、锁、凭据和重试；不要删除活跃锁。 |
| P06 压缩包损坏、截断、无任务根或多任务根 | 源包有缺陷时，重新整理完整单题包并上传；核对唯一 task.toml。 | 平台先检查下载完整性，提供损坏位置／重复路径；传输损坏先重取原包。 |
| P07 具体 wheel 下载 403／代理 DNS 530 | 核对依赖来源、版本和哈希，按约定提供资产。 | 平台检查失败 URL、出口、代理、授权及缓存；下载拒绝不等于包不存在。 |
| P08 镜像上传 blob upload unknown／PUT 404 | 通常无需改题包；保留当前版本。 | 平台修复 registry 上传会话、代理和发布，回读 manifest／digest。 |
| P09 模型／公开资产下载 429、TLS、重定向或超时 | 写清真实资产、版本、授权获取方式和校验；失效链接按实际提供方更新。 | 平台处理缓存、证书、重定向和限流；不绕过资产授权或 TLS 校验。 |
| P10 npm 代理认证 407 | 核对 npm 实际使用 bnpm，且未被后续命令覆盖。 | 平台处理构建身份的代理认证；不要把凭据写入题包或镜像层。 |
| P11 manifest／digest 解析失败；代理 not found；blob 401 | 核对自己控制的镜像引用与架构。 | 平台检查代理、认证及镜像发布完整性；代理错误不证明上游镜像不存在。 |
| P12 COPY／cache key 路径 not found | 按真实 context 修正 COPY／ADD，补齐文件并检查 .dockerignore；不要建空资产应付。 | 平台提供失败行及实际 context；平台选错 context 时由平台修复。 |
| P13 apt install 退出 100，无具体错误 | 取得第一条致命错误后，针对下载、版本或目录问题修改；不要盲目换包。 | 平台提供失败步骤完整 stdout／stderr 和 Dockerfile 行。 |
| P14 APT 锁定版本在源中找不到 | 核对发行版、updates／security 源和版本集合，改成可用、可复现的组合。 | 平台提供实际源和可用版本信息；不以全部取消锁定代替定位。 |
| P15 pip ResolutionImpossible | 根据冲突链修 requirements／constraints 中不相容的依赖组合。 | 平台提供完整解析报告，说明是否替换过环境或依赖。 |
| P16 prepare_image.py／uv sync 等准备步骤失败 | 修明确指向题包脚本、路径或资产的问题，保留完整性校验。 | 平台提供 traceback、失败子命令及 stderr；不凭最后一行猜根因。 |
| P17 证书包安装所需临时目录缺失 | 修 Dockerfile 步骤顺序、目录初始化、属主与所需权限。 | 平台核对构建目录是否被覆盖；保留证书验证，不关闭 TLS。 |
| P18 fixture 哈希不符／Hidden 初始化目录缺失 | 核对私有资产版本、manifest、读取／生成路径，按约定安全补交缺失资产。 | 授权维护方检查复制／注入和实际资产版本；不把 Hidden 公开给 Agent。 |
| P19 题包路径 Permission denied | 核对必需目录、文件和执行位，仅修实际所需权限。 | 平台核对解包／挂载和运行身份；不要求整包 chown／chmod。 |
| P20 bootstrap 解释器无法启动 | 题包控制路径时，核对解释器、动态链接、PATH、入口和执行权限。 | 平台提供启动契约及原始错误；平台注入的解释器／环境问题由平台修复。 |
| P21 sudoers／visudo 校验失败 | 规则来自题包时修正语法并保持最小授权。 | 平台注入规则由平台修；不开放无限 sudo 解决语法错误。 |
| P22 Docker Hub manifest 明确返回 429 | 保留正确镜像引用，通常无需修改题包。 | 平台使用授权缓存／同步、降低请求并按限流响应退避。 |
| P23 创建用户时 UID 1000 已存在 | 核对基础镜像已有用户及创建逻辑，保持题目要求的身份／权限关系。 | 平台提供实际镜像和身份契约；不要随意换 UID 破坏挂载权限。 |
| P24 sudo 资产所有源均下载失败，缺 HTTP 首因 | 核对资产地址和校验；明确失败原因后修对应源包问题。 | 平台导出各源状态、代理和 DNS 错误；不要猜根因或删掉资产约束。 |
| P25 Python 依赖哈希校验失败 | 核对锁文件、实际 wheel、版本和可信来源，确认正确资产后更新匹配哈希。 | 平台核对缓存／镜像是否返回错误文件；不要删除 --require-hashes。 |

## Agent 执行阶段

| 编号／报错现象 | 专家检查和修改 | 平台处理或提供 |

| E01 工作目录可写性预检拦截 | 注明只读资产和允许输出路径，只修与题目合同冲突的权限。 | 平台核对预检、挂载和身份；设计只读目录不必整目录开放。 |
| E02 HOME／缓存／临时／日志／PID 无权限 | 检查题包负责的初始化和输出目录，保持题目资产只读。 | 平台核对实际身份、挂载及注入路径；按真实控制点修复。 |
| E03 Agent 超时 | 先确认是否正常用尽预算、是否保存有效候选；题包入口／环境缺陷按反馈修正。 | 平台提供终止原因、候选和评分结果；正常截止且有可信评分不自动要求专家重跑。 |
| E04 NonZeroAgentExitCodeError／非零退出 | 按首条失败命令检查入口、依赖和路径；不按退出码猜根因。 | 平台提供完整 stderr 和启动契约，检查启动／身份问题。 |
| E05 LLMRefusalError／模型安全拒绝 | 保留原任务和授权说明，不改提示规避安全限制。 | 平台／负责人核对适用政策与支持渠道，不当作普通代码故障处理。 |
| E06 已结束但没有原生结果摘要 | 先保留当前题包及已有对应记录；通常不先改题。 | 平台核对 batch 日志、退出码、result／complete.json 和上传回执；不补造分数。 |
| E07 healthcheck 失败／socket 不存在 | 服务由题包负责时，修启动、路径、顺序与就绪条件；不要直接删检查。 | 平台核对挂载、进程启动和就绪日志，定位未完成环节。 |
| E08 CgroupCreationFailed／quota 参数错误 | 提供真实资源需求和当前配置；错误源参数由控制方修正。 | 平台检查后端支持范围、请求 ID 和资源路由；不为“跑通”擅自降低需求。 |
| E09 沙箱任务／会话不存在 | 通常没有题包修改动作，保留对应运行信息。 | 平台核对创建、重试、清理和回收记录，处理使用了已删除会话的问题。 |

## Verifier 评分与结果回传阶段

| 编号／报错现象 | 专家检查和修改 | 平台处理或提供 |
|-|-|-|
| S01 RewardFileNotFoundError | 评分未生成或写错位置时，修正式入口、异常分支和输出路径；保留真实失败原因。 | 平台核对 Verifier 退出码／日志与实际读取位置；已生成但未读到的按读取／回传链处理。 |
| S02 DownloadVerifierDirError | 核对题包声明输出位置；源包路径确有错误时修正。 | 平台检查产物是否存在、下载／归档／会话回收与回执；退出 0 不证明已回传。 |

多个 reward 文件不一定冲突：先确认平台真正读取哪个文件、是否存在合法聚合，以及该值是否对应当前候选。保留原始指标和原始分数，不能为了“通过”手工覆盖结果。
